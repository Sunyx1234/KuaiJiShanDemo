# 正泰集团厂区运营中心 —— 后台管理平台技术方案

> 版本：1.0
> 状态：评审稿
> 关联系统：正泰集团厂区综合态势运营中心（大屏）/ 移动作业端

---

## 1. 背景与目标

### 1.1 背景

现有系统是一套「前端大屏 + 极薄 Serverless」的展示型应用，覆盖集团三维地球、园区下钻、安全监控、访客定位、告警工单闭环等功能。随着业务演进，需要将以下能力从大屏中剥离，收敛到一个统一的**后台管理平台**：

1. **业务流监控处理**：对工单、告警等业务流程的运行状态进行统一监控、催办、督办与 SLA 管理。
2. **用户权限管理**：统一的账号、角色、菜单/接口权限与数据范围（按组织、按园区）管控。
3. **低代码审批流配置**：通过可视化方式配置审批流程节点、审批人策略、超时规则与表单字段。
4. **组织管理**：集团 → 基地/园区 → 部门 → 岗位的组织树与人员主数据。

### 1.2 目标

- 建设一个**独立部署**的后台管理平台（独立前端 + 独立后端 + 关系型数据库）。
- 引入**成熟审批流引擎**，实现可配置、可监控、可扩展的审批流能力。
- 建立**RBAC + 数据权限 + 组织树**的统一权限底座。
- 将现有告警工单闭环**迁入**新后端，作为审批流引擎的第一个落地业务。
- 保持大屏与移动作业端的用户体验不回退，只做「数据源与交互语义」的收敛，不做视觉重构。

### 1.3 非目标（本阶段不做）

- 不做大屏视觉/交互重构（只改数据来源与工单状态语义）。
- 不在一期自研完整 BPMN 可视化设计器（先采用成熟引擎自带能力，逐步增强）。
- 不引入多租户（SaaS 级租户隔离暂不纳入，仅按园区/组织做数据范围隔离）。

## 2. 现状评估

### 2.1 现有架构简述

```text
浏览器
 ├─ 大屏 SPA（Vue3 + Pinia + Router + ECharts + Three.js）
 ├─ 移动作业端（/#/work-order）
 └─ 静态资源（Netlify/EdgeOne 托管）
        │
   API /api/work-orders, /api/video-urls
        │
 Netlify Functions / EdgeOne Pages Functions
   ├─ work-orders.mjs（工单闭环：派单/接单/复核/归档 + 飞书通知）
   ├─ video-urls.mjs（阿里云 OSS 视频签名）
   └─ 存储：@netlify/blobs / @edgeone/pages-blob（KV 键值）
```

### 2.2 与目标的差距

| 目标能力 | 现状 | 差距 |
|---|---|---|
| 业务流监控处理 | 工单状态机硬编码在 `types.ts` + `CenterScene.vue`（6 步 stepper）+ `work-orders.mjs` 分支 | 无流程定义/实例抽象，无任务中心、无超时/SLA、无督办 |
| 用户权限管理 | 仅 `WORK_ORDER_ADMIN_PIN` 环境变量 + sessionStorage 口令 | 无用户/角色/权限/登录态/数据范围 |
| 低代码审批流 | 无 | 从零建设，是工作量最重的模块 |
| 组织管理 | 仅 `FEISHU_RECEIVER_NAME/DEPARTMENT` env + mock 字段 | 无组织树/部门/岗位/人员主数据 |

### 2.3 关键结论

- 现有后端是「Serverless Functions + KV 存储」，**没有关系型数据库、事务、统一鉴权与查询能力**，无法承载 RBAC、审批流引擎、组织树、审计日志。
- 现有前端「数据按园区隔离」缺失：`dashboardStore` 是全局单例，mock 直接 import，切园区数据不变。数据权限要在后端重新建模。
- **必须新建一个真正有数据库的后端服务**，现有 edge functions 仅保留 OSS 签名等边缘友好能力。

## 3. 技术选型

### 3.1 后端语言/框架

| 方案 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| **Java + Spring Boot 3**（推荐） | 审批流开源生态最成熟（Flowable/Camunda/Activiti 均为 Java）；自部署标准形态；生态与招聘资源丰富 | 相对 Node 略重 | ✅ 首选 |
| Node.js + NestJS | 与现有前端同构，飞书代码可直接复用 | 成熟审批流引擎缺失，需自研或弱绑定；TS 类型在长期大型后端项目中的工程化成本更高 | 备选 |
| Go + Gin | 性能好、部署简单 | 审批流生态几乎空白 | 不选 |

> 决策依据：团队无栈偏好 + 需求「审批流引入成熟引擎」。成熟审批流引擎几乎只存在于 Java 生态，故选 Java。

### 3.2 审批流引擎

| 引擎 | 许可 | 成熟度 | 低代码能力 | 自部署成本 | 结论 |
|---|---|---|---|---|---|
| **Flowable 7.x** | Apache 2.0 | 高（Activiti 正统分支，最活跃） | 自带 BPMN/CMMN/DMN Modeler、Task 任务中心、Admin 流程监控、IDM | 低（内嵌 Spring Boot） | ✅ 首选 |
| Camunda 7 | Apache 2.0 | 高 | 强（Modeler 体验好） | 低 | 备选（7 已进维护期） |
| Camunda 8 | 源码开放/企业版 | 高 | 强 | 高（需 Zeebe + ES/OpenSearch，自托管重） | 不选 |
| Activiti | Apache 2.0 | 中（社区较沉寂） | 中 | 低 | 不选 |
| Zeebe | 源码开放 | 中 | 强 | 高 | 不选 |

> 决策：**Flowable 7.x**。它是 Activiti 的正统延续、社区最活跃、开源版自带任务中心/流程监控/身份组件，最贴合「成熟引擎 + 自部署」的需求。

> ⚠️ 现实提醒：Flowable 开源的**表单设计器体验有限**（更强能力在其商业版 Work/Engage）。因此低代码表单建议自研（用 `form-create` 做拖拽表单设计器），流程设计器可采用开源 `bpmn-js` 或 Flowable Modeler 白标方案。

### 3.3 数据库

| 方案 | 优势 | 结论 |
|---|---|---|
| **PostgreSQL 16**（推荐） | JSONB 天然支持审批动态表单字段；可靠性/事务/扩展性均衡 | ✅ 首选 |
| MySQL 8 | 运维熟悉度高 | 备选 |

### 3.4 其余组件

| 组件 | 选型 | 说明 |
|---|---|---|
| 持久层 | MyBatis-Plus（或 Spring Data JPA） | 组织/RBAC 用 MyBatis-Plus 更顺手 |
| 缓存/会话 | Redis 7 | 登录态、验证码、限流、流程热点缓存 |
| 认证鉴权 | Spring Security + JWT + RBAC | 后台登录与接口鉴权 |
| 后台前端 | Vue 3 + TypeScript + Element Plus + Vite + Pinia | 与现有大屏同构，复用团队技能 |
| 对象存储 | 阿里云 OSS（沿用现有）+ MinIO 本地兜底 | 工单照片/告警截图 |
| 反向代理/静态托管 | Nginx | 托管后台前端 + 大屏（可选）+ 反向代理 |
| 可观测 | Prometheus + Grafana（可选），SLF4J 结构化日志 | 监控与排障 |

## 6. 核心设计

### 6.1 权限模型（RBAC + 数据权限）

- **功能权限**：用户 ↔ 角色 ↔ 菜单/按钮/接口（`sys_user_role`、`sys_role_menu`）。菜单表 `type` 区分目录/菜单/按钮，按钮对应接口 `perms` 标识。
- **数据权限**：角色 `data_scope` 字段定义范围：
  - `1` 全部数据
  - `2` 自定义部门（配 `sys_role_dept`）
  - `3` 本部门及以下
  - `4` 仅本部门
  - `5` 仅本人
- **园区维度数据权限**：`sys_role_park`（角色 ↔ 园区），用于「按园区隔离」的业务数据（设备/摄像头/告警/工单）。查询时统一注入数据范围条件。
- **登录态**：JWT（access + refresh），Redis 存会话/黑名单；密码 BCrypt 存储。

### 6.2 组织模型

- 组织树用 `sys_dept` 的 `parent_id + ancestors` 表达，支持集团 → 基地/园区 → 部门 → 小组。
- `sys_dept.park_id`（可空）将组织节点与业务园区关联，便于「组织归属 + 园区数据范围」联动。
- 用户与部门（`sys_user.dept_id`）、用户与岗位（`sys_user_post`）关联。

### 6.3 审批流模型（Flowable 集成）

**核心原则：业务表与流程引擎解耦。**

- Flowable 负责「流程流转 + 任务分配 + 历史」，不存业务字段。
- 业务表（`work_order`）存业务数据，用 `process_instance_id` 双向关联。
- 流程定义变更（BPMN 升级）不影响业务表结构。

```text
ai_alert(告警) ──派单──> work_order(工单) + Flowable 流程实例
                            │ process_instance_id
                            ▼
                    ACT_RU_EXECUTION / ACT_RU_TASK(待办) / ACT_HI_*(历史)
```

**状态映射（前端枚举 → 引擎语义）**：

| 现状（前端写死） | 后台目标 |
|---|---|
| `AiAlertStatus`（待确认/待派单/处理中/待复核/已归档/已排除） | 告警业务快照（保留在 `ai_alert.status`）+ 流程实例的当前任务节点（Flowable 权威） |
| `WorkOrderProgress`（待接单/已接单/已处置） | Flowable 用户任务节点（派单→接单→处置→复核→归档） |
| `CenterScene.vue` 6 步 stepper | 改为渲染 `ACT_HI_*` 历史 + 当前任务节点，由后端下发 |

**第一个落地流程（告警处置工单）BPMN 节点规划**：

```text
[开始] → 确认告警(人工/值班员)
       → 派单(人工/值班员)
       → 接单(人工/现场责任人)
       → 现场处置并提交(人工/现场责任人, 上传照片)
       → 复核归档(人工/管理员, 通过/退回)
       → [结束]
每节点支持：审批人策略(指定人/角色/发起人上级)、超时(计时器边界事件)、退回、催办
```

### 6.4 低代码审批流配置

- **流程设计**：BPMN 2.0（Flowable Modeler / bpmn-js），支持节点、连线、条件、审批人策略、超时。
- **表单设计**：自研 JSON Schema 表单（`form-create` 拖拽生成），表单定义存 `workflow_form_definition`，实例数据存 `workflow_form_data`（JSONB）。
- **配置项**：流程分类、是否启用、版本、超时 SLA、通知渠道。

### 6.5 通知集成

- 复用现有 `work-orders.mjs` 中的飞书逻辑（`getTenantToken`/`sendFeishuOrder`/`buildFeishuCard`），迁为 `FeishuNotifier` 服务。
- 统一通知模型：`notify_log` 记录渠道（飞书/短信）、状态（待发送/发送成功/发送失败）、发送时间、失败原因，支持重试。
- 短信第一阶段保留占位，接入真实供应商后启用。

### 6.6 业务流监控

- 基于 Flowable 历史表 + 业务表，提供：待办任务数、超时任务、节点平均耗时、SLA 达成率、按园区/部门维度的工单看板。
- 支持催办、督办、超时告警、委托/转办。
- 大屏「事件处置流程」区域可反向对接该监控接口，保持现状视觉但数据实时化。

## 10. 里程碑

### P0 —— 地基（约 4-6 周）

- 后端服务 + PostgreSQL + Spring Security/JWT + RBAC + 组织树 + 岗位 + 字典。
- 现有工单闭环迁入后端并落库跑通（先不接 Flowable，先落库）。
- 大屏/移动端切换数据源，功能不回退。
- **验收**：后台可登录、管用户/角色/组织；工单闭环全链路可用。

### P1 —— 流程化（约 4-6 周）

- 接入 Flowable，将「告警处置工单」建为第一个 BPMN 流程。
- 接入飞书/短信通知；上线任务中心 + 流程监控（待办/已办/催办/超时）。
- **验收**：工单走流程引擎，可监控节点、可催办、可超时告警。

### P2 —— 低代码 + 监控（约 6-8 周）

- 审批流配置界面（BPMN 设计器）+ 低代码表单设计器（form-create）。
- 数据权限（按部门/园区范围）落地。
- 业务流监控看板（工单 SLA/超时/节点耗时），并可反哺大屏。
- **验收**：非研发可配置新流程；按组织/园区隔离数据；监控看板可用。

### P3 —— 规模化（约 4-6 周）

- 多园区接入（`park` 维度数据隔离落地）、审计日志完善、SLA/超时告警、短信正式供应商。
- **验收**：多园区数据隔离正确，审计可追溯，通知可靠。

## 11. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 低代码表单体验不足（开源引擎短板） | 高 | 表单设计器自研（form-create），单独估算工作量；不依赖引擎自带表单 |
| 数据权限（园区/部门）返工 | 高 | 从 P0 就建模 `park_id` + `data_scope` + `sys_role_park`，查询统一注入范围条件 |
| Flowable 与业务表状态不一致 | 中 | 以流程引擎为权威，业务表存快照；通过 `process_instance_id` 双向核对，加一致性对账任务 |
| 现有 store 无 parkId 维度，改造波及面大 | 中 | 大屏数据源切换与后端 P0 并行，store 重构单独立项排期 |
| 一次性移动端 token 滥用 | 中 | token 绑定 Flowable task，限时 + 一次性消费 + 操作审计 |
| 飞书/短信通知可靠性 | 中 | 统一 `notify_log` + 重试 + 失败告警 |
| 单点后端可用性 | 低 | 一期单实例可接受；二期无状态化 + 主备 DB |

## 12. 非功能需求

- **安全**：密码 BCrypt、JWT 过期/刷新、接口级鉴权、操作审计、敏感字段脱敏（访客姓名等延续现状）。
- **性能**：工单列表/看板走业务表 + 索引；Flowable 历史查询走 `ACT_HI_*`；列表分页。
- **可观测**：结构化日志（traceId）、Prometheus 指标、慢 SQL 监控。
- **兼容**：大屏与移动端现有 URL、视觉、交互不回退；`/api/work-orders` 路径兼容。
