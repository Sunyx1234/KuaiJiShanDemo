# 正泰集团厂区运营中心——管理后台与生产化演进规划

> 版本：1.0  
> 日期：2026-08-17  
> 状态：规划评审稿  
> 适用范围：现有大屏 Demo、拟建管理后台、后续 Pilot 与生产化建设  
> 关联文档：《后台管理平台技术方案》《整体大屏需求》《开发交接文档》

---

## 1. 文档目的

本文档用于回答以下问题：

1. 当前大屏 Demo 下一步为什么要建设管理后台；
2. 每个阶段要验证什么，而不是简单堆叠什么功能；
3. Demo、Pilot 和生产系统之间的边界是什么；
4. 哪些条件满足后，才进入下一阶段；
5. 如何让其他开发人员愿意接手并快速完成第一次有效修改；
6. 如何将本项目经验沉淀为可复用的 Demo 生成流水线。

本文档负责定义**阶段、目标、范围和准入门槛**。《后台管理平台技术方案》中的 Spring Boot、PostgreSQL、Flowable、RBAC 等内容属于候选目标架构，不代表必须在第一阶段全部实施。

## 2. 当前基线与核心判断

### 2.1 当前系统基线

现有系统已经具备：

- Vue 3 + TypeScript + Vite 大屏；
- 集团、园区两级展示；
- 综合态势、安全监控、访客管理主题；
- ECharts、Three.js 及多类交互组件；
- EdgeOne / Netlify 云函数；
- OSS 视频签名；
- AI 告警、工单派发、移动接单、处置、复核归档；
- 飞书通知与演示部署链路；
- 初步的数据库 DDL、后台技术方案和交接资料。

当前系统的准确定位为：

> **交互 Demo + 有限范围的真实技术验证。**

它已经超过纯静态原型，但尚不具备生产系统所要求的统一身份、权限、审计、数据治理、可靠性、测试、运维和责任体系。

### 2.2 当前主要问题

1. 大量业务数据和显示配置仍位于前端 Mock 文件；
2. 缺少可供业务人员维护主数据和演示场景的管理后台；
3. 指标定义、数据值和前端展示模型尚未完全分离；
4. AI 告警与工单生命周期存在一定语义混合；
5. 当前与远期目标架构混在同一方案中，容易造成一期范围过大；
6. 工单业务在不同 Serverless 平台存在逻辑分叉风险；
7. 缺少 API 契约和关键故事线自动测试；
8. 管理 PIN、移动 Token、文件上传和访客数据仅适合受控 Demo；
9. 新开发者启动、理解和完成首次修改仍依赖原作者经验。

### 2.3 总体建设原则

1. **先验证，再产品化**：没有稳定业务场景，不提前建设复杂平台能力；
2. **以任务为中心**：后台不是数据库表的简单集合；
3. **最小但可毕业**：当前实现保持简单，同时预留清晰升级接口；
4. **模块化单体优先**：业务边界清晰，但不提前引入微服务复杂度；
5. **单一事实来源**：业务对象、指标、接口和测试尽可能由统一规格派生；
6. **真实与模拟分离**：所有数据明确来源、质量和适用范围；
7. **安全与阶段匹配**：Demo 可以接受有限风险，但必须显式记录；
8. **生成与手写分离**：自动生成不得无提示覆盖人工扩展；
9. **以可接手性衡量质量**：项目不能只依赖原作者才能运行和修改；
10. **每阶段设退出条件**：不以“功能大致完成”作为进入下一阶段的依据。

## 3. 总体阶段路线

```text
P0 边界与模型基线
  ↓
P1 最小可用管理后台
  ↓
P2 有限真实业务 Pilot
  ↓
P3 生产就绪建设
  ↓
P4 组织化交付与规模维护
  ↓
P5 Demo Factory 产品化沉淀
```

建议周期仅用于工作量级判断，不构成项目承诺；具体排期应在每一阶段完成评审后重新估算。

| 阶段 | 核心目标 | 建议量级 |
|---|---|---:|
| P0 | 冻结验证边界，建立统一业务和数据模型 | 1～2 周 |
| P1 | 验证一个可用、好用、可重复搭建的管理后台 | 3～5 周 |
| P2 | 在有限用户和真实数据下验证业务闭环 | 4～8 周 |
| P3 | 补齐正式运行需要的安全、可靠性和运维能力 | 8～16 周以上 |
| P4 | 让多人可持续开发、发布和维护 | 与 P1～P3 并行，集中验收 2～4 周 |
| P5 | 将经验转化为标准化 Demo 生成流水线 | 持续演进 |

## 4. P0——边界与模型基线

### 4.1 阶段目标

在不建设完整后台的前提下，明确第一条需要验证的端到端业务链路，并将当前隐含在页面和代码中的业务认识显式化。

首选验证链路：

```text
园区 → 摄像头 → AI 告警 → 工单 → 处置结果 → 大屏更新
```

### 4.2 主要工作

#### 交付边界

- 编写一页式 Demo Charter；
- 明确哪些功能是真实能力、模拟能力和未来规划；
- 建立 Capability Map，标记 Demo / Validated / Pilot-ready / Production Gap；
- 明确本轮客户评审要验证的问题和不验证的问题。

#### 业务建模

- 定义园区、摄像头、AI 告警、工单四个核心业务对象；
- 分离 AI 告警和工单的生命周期；
- 定义对象关系、状态、动作和关键约束；
- 区分主数据、事件数据、配置数据和演示数据；
- 定义第一批指标的业务口径、维度、刷新频率和数据来源。

#### 架构决策

- 明确近期验证架构与远期产品架构；
- 选择管理前端、API、数据库和部署的第一阶段技术组合；
- 形成架构决策记录 ADR；
- 定义现有 Serverless Functions 的保留、迁移和退出边界；
- 确定管理后台作为独立应用还是同仓库独立子应用。

#### 安全基线

- 列出系统资产、用户角色和信任边界；
- 标记访客数据、视频、工单、飞书凭据和 OSS 凭据的数据等级；
- 记录当前 PIN、URL Token、文件上传等已知风险；
- 定义 Demo 阶段可接受风险和进入 Pilot 前必须解决的风险。

### 4.3 交付物

- `Demo Charter`；
- 核心业务对象与状态图；
- 指标定义清单；
- 数据分类与来源清单；
- 最小后台功能清单；
- 近期架构图；
- ADR 初始集合；
- 简版威胁模型；
- P1 验收故事和测试场景。

### 4.4 退出条件

- 业务方能够理解并确认四个核心对象的含义；
- AI 告警与工单状态不再混为同一个生命周期；
- 每个大屏关键指标至少有口径和数据来源；
- P1 范围中没有 Flowable、多租户、复杂组织等未验证能力；
- 技术选型得到未来维护方或产品部门的初步认可；
- P1 的关键用户任务可以被明确描述和验收。

### 4.5 本阶段明确不做

- 不开发完整后台；
- 不建设通用低代码平台；
- 不引入微服务；
- 不建设复杂权限和工作流；
- 不承诺生产部署。

## 5. P1——最小可用管理后台

### 5.1 阶段目标

验证以下核心假设：

> 业务人员可以通过后台维护大屏背后的核心对象和演示数据；开发人员可以通过统一规格快速增加一个业务对象；后台修改能够可靠反映到大屏。

### 5.2 最小功能范围

```text
管理后台
├── 工作台
├── 园区管理
├── 摄像头管理
├── AI 告警查询
├── 工单管理
├── 指标定义
├── 大屏数据绑定
├── 演示场景管理
└── 最小系统配置
```

#### 当前允许 CRUD 的数据

- 园区；
- 摄像头；
- 摄像头区域；
- 算法、告警级别等字典；
- 指标定义；
- 大屏绑定；
- 演示场景配置。

#### 只允许查询或有限操作的数据

- AI 告警；
- 工单；
- 工单时间线；
- 通知记录；
- 访客轨迹；
- 设备趋势。

事件数据不得被当作普通主数据任意修改。

### 5.3 技术目标

- 建立管理后台独立入口；
- 建立统一 API 层；
- 引入关系型数据库；
- 使用版本化 Migration 管理数据库；
- 区分 required、demo、optional Seed；
- 提供单管理员登录；
- 建立基础操作记录；
- 建立 OpenAPI 或等价 API 契约；
- 前后端共享或自动生成类型；
- 将至少一个现有 Mock 数据域切换到真实 API；
- 建立演示数据一键初始化和重置；
- 建立关键故事线自动冒烟测试。

### 5.4 UX 验证任务

后台必须围绕任务验证，而不是只验证表格是否能打开：

1. 新建一个园区并配置基础展示信息；
2. 为园区新增摄像头并配置位置、算法和视频地址；
3. 修改摄像头状态，并在大屏看到正确变化；
4. 查询严重告警并查看其来源摄像头；
5. 查看工单处理过程并完成当前已验证的复核操作；
6. 查看某个大屏指标的定义与数据来源；
7. 一键切换或重置客户演示场景。

### 5.5 交付物

- 最小管理后台；
- 统一 API；
- 数据库 Migration 与 Seed；
- 核心业务 API 契约；
- 管理后台操作手册；
- Demo 数据重置命令；
- 关键故事线测试；
- P1 使用反馈记录；
- P2 Production Gap 清单。

### 5.6 退出条件

- 在后台修改一个摄像头或园区，大屏无需修改代码即可更新；
- 非开发人员可以在无口头指导下完成主要任务；
- 演示数据可以重复初始化并获得一致结果；
- API、数据库和前端对核心字段的理解一致；
- 核心故事线可以自动或半自动验证；
- 新开发人员能在 30 分钟内启动项目；
- 新开发人员能在半天内完成一个简单字段的前后端贯通；
- 尚未确认的业务流程没有被提前固化为复杂工作流。

### 5.7 本阶段明确不做

- 不做企业统一 SSO；
- 不做完整组织和多租户；
- 不做字段级数据权限；
- 不做 BPMN 流程设计器；
- 不做高可用和灾备集群；
- 不按正式生产 SLA 承诺。

## 6. P2——有限真实业务 Pilot

### 6.1 阶段目标

在明确的用户、园区、数据和时间范围内，验证系统是否能够支持真实业务操作，而不仅是演示。

Pilot 必须有明确边界，例如：

```text
一个园区
一个值班团队
一种 AI 告警
一条工单处置流程
四周试运行
人工支持兜底
```

### 6.2 主要工作

#### 真实数据接入

- 将 Mock 数据通过 Adapter 替换为有限真实数据源；
- 保留 Mock / Real / Hybrid 模式标记；
- 建立数据质量、延迟和缺失状态；
- 明确每个数据源的负责人和失败处理方式。

#### 身份与权限

- 引入真实用户身份；
- 建立最小角色集，例如管理员、值班员、现场责任人、复核人；
- 仅实现已确认的园区或部门数据范围；
- 建立登录、权限和关键操作审计。

#### 业务闭环

- 将工单状态机从页面逻辑收敛到领域服务；
- 明确状态权威来源；
- 加入通知失败重试、幂等和重复操作保护；
- 加入移动 Token 过期、撤销和任务绑定；
- 建立文件上传类型、大小和访问控制；
- 记录处置结果和客户反馈。

#### Pilot 运维

- 建立测试或预生产环境；
- 建立错误监控和基础业务监控；
- 建立数据库备份与一次恢复演练；
- 建立 Pilot 支持群、问题分级和人工兜底；
- 建立试点结束、暂停和回退条件。

### 6.3 何时才考虑 Flowable

仅在同时满足以下条件后评估引入 Flowable：

- 至少一条流程已在真实使用中稳定运行；
- 流程节点、角色、退回和超时规则得到业务确认；
- 存在多条流程或频繁变更需求；
- 简单状态机已经明显成为维护瓶颈；
- 产品部门认可引擎带来的运行和维护成本。

若只存在一条稳定工单流程，继续使用清晰、可测试的领域状态机通常更合适。

### 6.4 交付物

- Pilot 方案与范围声明；
- 真实数据 Adapter；
- 最小真实身份和权限；
- 操作审计；
- 数据质量监控；
- 通知与文件安全加固；
- Pilot 运维手册；
- 备份恢复记录；
- 试点反馈和业务结果报告；
- 正式生产差距清单。

### 6.5 退出条件

- 限定用户能够完成真实端到端业务；
- 没有依赖共享 PIN 完成管理操作；
- 关键操作可以追溯到真实用户；
- 数据来源和质量对用户可见；
- 通知失败、第三方不可用和重复提交有明确处理方式；
- 数据库恢复演练成功；
- Pilot 期间问题、人工介入和业务效果有完整记录；
- 业务方正式决定是否进入生产化。

### 6.6 本阶段明确不做

- 不默认扩展到全集团；
- 不承诺 7×24 高可用；
- 不在流程尚未稳定时建设通用流程平台；
- 不因单个客户特例破坏核心模型。

## 7. P3——生产就绪建设

### 7.1 阶段目标

将已经通过 Pilot 验证的业务能力，建设为具备正式所有者、安全边界、可靠性目标和持续运维能力的生产系统。

### 7.2 产品与治理

- 明确产品负责人、业务规则负责人、数据负责人和技术负责人；
- 明确正式用户范围、服务时间和支持渠道；
- 建立需求变更和版本发布机制；
- 建立事故分级、响应和复盘机制；
- 完成正式验收和责任边界确认。

### 7.3 安全建设

- 接入企业 SSO 或正式身份系统；
- 完整 RBAC 和已确认的数据权限；
- 服务账号与个人账号分离；
- 密钥托管、轮换和最小权限；
- 完整威胁模型和安全评审；
- 输入验证、限流、防注入、防越权；
- 文件上传安全和私有访问；
- 依赖和镜像漏洞扫描；
- 敏感日志清理；
- 访客数据最小化、脱敏、保留和删除规则；
- 必要的渗透测试和整改。

### 7.4 数据治理

- 主数据和指标负责人；
- 指标口径审批和版本管理；
- 数据血缘和来源记录；
- 数据质量规则和告警；
- 数据更正和删除流程；
- 导出权限和审计；
- 数据库迁移、回滚和兼容策略；
- 正式备份策略与定期恢复演练。

### 7.5 可靠性与可观测性

- 定义 SLO、可接受停机时间、数据丢失目标和恢复时间目标；
- 无状态服务和必要的水平扩展；
- 健康检查、超时、重试、幂等和降级；
- 结构化日志、traceId、错误追踪；
- API 成功率和延迟监控；
- 数据库慢查询和容量监控；
- OSS、飞书等第三方依赖监控；
- 通知成功率、工单超时等业务监控；
- 正式告警规则和处理 Runbook。

### 7.6 测试与发布

- 单元测试；
- API 契约测试；
- 数据库 Migration 测试；
- 权限和越权测试；
- 集成测试；
- 关键用户旅程 E2E；
- 性能与容量测试；
- 安全测试；
- 发布后冒烟测试；
- CI/CD、审批、灰度和回滚；
- 开发、测试、预生产、生产环境隔离。

### 7.7 交付物

- Production Readiness Review；
- 正式架构和部署拓扑；
- SLO 与监控面板；
- 安全评审和整改记录；
- 数据治理方案；
- CI/CD 与回滚机制；
- 备份和灾难恢复方案；
- 运维、故障和客户支持手册；
- 正式版本和验收报告。

### 7.8 退出条件

- 产品、数据、技术和运维所有者明确；
- 正式身份、权限和审计已上线；
- 安全评审问题关闭或有明确风险接受人；
- 备份恢复、发布回滚和关键故障演练通过；
- 监控告警能够覆盖技术和核心业务异常；
- 关键旅程、权限和 Migration 自动测试通过；
- 生产支持和事故响应机制已建立；
- 正式验收完成。

## 8. P4——组织化交付与规模维护

> 本阶段的基础工作应从 P1 开始持续建设，不应等到生产上线后补文档。

### 8.1 阶段目标

让项目从“原作者能维护”升级为“团队能够安全、持续地开发和运行”。

### 8.2 工程体验目标

- 新开发者 30 分钟内启动必要服务；
- 1 小时内理解系统主要模块和请求链路；
- 半天内完成一个简单字段的前后端修改；
- 1 天内完成一个简单业务对象的 CRUD 和测试；
- 不依赖原作者口头指导完成首次有效变更。

核心指标：

> **Time to First Successful Change：新开发者完成第一次正确修改所需时间。**

### 8.3 主要工作

#### 仓库和模块边界

- 大屏、后台、API 作为独立应用；
- 共享业务定义和 API 契约；
- 领域逻辑与 EdgeOne、Netlify、OSS、飞书等平台适配层分离；
- 自动生成目录和人工扩展目录分离；
- 禁止在页面组件中直接承载核心业务状态机。

#### 开发者 Golden Path

- 一条命令安装；
- 一条命令启动；
- 一条命令初始化或重置演示数据；
- 一条命令执行完整验证；
- 提供可直接使用的测试账号和脱敏数据；
- 提供常见变更操作手册。

#### 核心文档

```text
README.md           如何启动和验证
ARCHITECTURE.md     系统边界、模块和请求链路
DOMAIN.md           对象、关系、状态、动作和指标
CONTRIBUTING.md     分支、提交、PR 和测试规则
SECURITY.md         安全边界、凭据和风险
RUNBOOK.md          部署、回滚、恢复和故障处理
docs/adr/           架构决策记录
docs/recipes/       常见修改操作指南
```

#### 团队治理

- 明确模块 Owner 和 Code Owner；
- 建立 PR 模板和 Definition of Done；
- 重要架构变化采用 ADR 或轻量 RFC；
- 建立版本、变更日志和弃用策略；
- 建立依赖升级和安全修复机制；
- 产品部门从业务模型、API 和部署约束阶段开始参与，而不是最终接收代码。

### 8.4 退出条件

- 至少一名非原作者独立完成端到端变更；
- 新开发者上手过程有计时和问题记录；
- 生成代码不会无提示覆盖人工代码；
- 业务对象和接口变更有明确评审路径；
- 平台适配和领域逻辑不存在明显重复；
- 离开原作者后，项目仍可以构建、部署和排障。

## 9. P5——Demo Factory 产品化沉淀

### 9.1 阶段目标

将项目建设经验沉淀为可重复执行的 Demo 生成流水线：

```text
一句业务目标
  → 多轮需求澄清
  → ProjectSpec
  → 需求说明书
  → 业务对象与指标
  → 数据库和 API
  → 管理后台和大屏
  → 演示数据
  → 自动测试
  → 预览和部署
```

### 9.2 核心资产

- 需求澄清协议；
- `ProjectSpec` Schema；
- 业务对象、状态机和指标模板；
- 管理后台 CRUD 引擎；
- 大屏组件与数据绑定规范；
- 数据库、API、前端和测试生成器；
- Demo 场景和 Seed 生成器；
- 部署 Profile；
- Codex Skills、脚本和模板；
- Golden Samples 和自动评测集。

### 9.3 生成治理

每次生成应记录：

- 输入需求；
- 澄清结论；
- ProjectSpec 版本；
- 生成器版本；
- 生成文件清单；
- 人工扩展点；
- 与上次生成的差异；
- 自动测试结果；
- 部署结果。

生成目录和手写目录必须明确分开：

```text
generated/   自动生成，可重复构建
custom/      人工扩展，生成器不得覆盖
```

### 9.4 评测指标

- 从一句话到首次预览的时间；
- 平均澄清轮数；
- 首次构建成功率；
- 自动测试通过率；
- 人工修改比例；
- 需求变化后的安全重生成率；
- 部署成功率；
- 客户首轮验收通过率；
- 新开发者首次有效变更时间；
- 同类项目的模板复用率。

### 9.5 退出条件

- 至少沉淀 5～10 个具有代表性的 Golden Samples；
- 同类型后台可以从 ProjectSpec 稳定生成；
- 生成项目有完整启动、测试和部署方式；
- 需求变化后可以差异化更新，不破坏人工扩展；
- 非原作者可以使用流水线完成一个新 Demo；
- 生成结果能够清楚标记 Demo、Pilot 和 Production Gap。

## 11. 阶段评审与变更机制

### 11.1 每阶段评审问题

1. 本阶段减少了什么业务不确定性？
2. 哪些假设被客户确认，哪些被否定？
3. 哪些能力仍然只是演示？
4. 是否出现了真实用户、真实数据或真实操作？
5. 安全和责任边界是否需要升级？
6. 是否满足本阶段退出条件？
7. 下一阶段新增复杂度是否有明确业务依据？

### 11.2 进入下一阶段的决策

每次阶段升级必须输出：

- 已验证结论；
- 未解决问题；
- 新阶段范围；
- Production Gap；
- 负责人；
- 验收标准；
- 排期和资源估算；
- 风险接受人。

未满足退出条件时，不应通过增加更多模块来掩盖当前问题。

## 12. 主要风险与应对

| 风险 | 表现 | 应对 |
|---|---|---|
| 后台范围失控 | 从 CRUD 快速扩展为完整 OA/低代码平台 | 每阶段维护明确非目标 |
| 需求不明确却提前固化流程 | Flowable、组织、权限反复返工 | 先状态机和真实案例验证 |
| 技术栈与产品部门不兼容 | Demo 可用但正式团队无法接手 | P0 邀请维护方参与技术决策 |
| 数据与展示耦合 | 修改指标需要修改多个组件 | 分离指标定义、指标值和显示模型 |
| AI 生成覆盖人工修改 | 开发人员不敢维护生成代码 | generated/custom 分离与差异更新 |
| 多平台业务逻辑分叉 | EdgeOne 与 Netlify 行为不同 | 领域核心一份，平台 Adapter 多份 |
| Demo 凭据进入生产 | PIN、URL Token 被误当正式安全 | 每阶段安全门槛和风险标记 |
| 原作者成为单点 | 其他人无法启动、修改和排障 | Golden Path、Recipes、结对验收 |
| 功能多但不可验证 | 演示路径经常回归 | 关键故事线自动验收 |
| 生产责任不清 | 上线后无人维护和响应 | P3 前明确产品、技术、数据和运维 Owner |

## 13. 当前推荐决策

1. 现阶段停留在 P0，不启动完整后台或生产架构建设；
2. 以“园区—摄像头—AI 告警—工单”为第一条验证链；
3. P1 只验证最小后台、统一 API、数据库、数据绑定和演示重置；
4. 暂不引入 Flowable、多租户和复杂组织权限；
5. 将现有《后台管理平台技术方案》保留为候选远期架构，不作为一期承诺；
6. 从 P0 开始邀请未来维护方参与业务模型、API 和技术约束评审；
7. 将“新开发者首次有效变更时间”与“关键故事线自动通过率”作为核心工程指标；
8. P1 完成后再决定是采用 Forge Admin、借鉴其配置模型，还是继续自建轻量后台；
9. 每次演进都维护 Demo / Pilot / Production Gap，而不是将 Demo 默认包装为生产能力；
10. 最终将验证成功的流程固化为 ProjectSpec、生成器、Skill、模板和评测集。

## 14. 总结

本项目的长期价值不只是建设一个管理后台，而是形成以下可迁移能力：

```text
理解业务问题
  → 建立最小业务模型
  → 选择最小可毕业架构
  → 快速生成大屏与后台
  → 通过真实任务验证
  → 明确生产差距
  → 安全地交给团队持续建设
```

阶段规划的核心原则是：

> **每增加一层架构复杂度，都必须对应一个已经出现并被验证的业务、交付或运行问题。**

只有这样，Demo 才不会过早膨胀为无人维护的平台，也不会在进入正式产品阶段时因为缺少边界、契约和证据而被全部推倒重来。
