# 订单生命周期与大屏展示规划

依据：用户提供的《销售订单流_脱敏混淆(1).xlsx》，包括“业务表单”说明及 17 个业务表结构。本文记录页面与数据映射规划。当前页面已实现演示结构，尚未导入脱敏样例或接入真实业务接口。

## 业务主线

销售要货申请 → 要货计划审批/汇总 → 销售订单及支付项目 → 要货单 → 发货通知及排车 → ERP销售发货 → ERP销售出库 → CRM出库回写 → 配送送达 → 客户签收。

这份数据主要覆盖销售订单的履约生命周期。销售要货计划并不是生产计划或原料采购计划；ERP中的批号、质检标志和生产订单引用，也不能替代MES工艺执行、LIMS检测结果和设备采集记录。订单支付项目尚需区分资金、折扣、货补、政策优惠及真实现金流水。

## 页面分工

### 地球页：销售流向与交付网络

- 左侧：统计期内订单数、订单金额、客户/地区覆盖、区域订单排行；订单列表保留暂停与轮播选择。
- 中央：绍兴园区至客户所在城市的连线。订单流向、出库流向、配送状态使用明确的类型标签；没有车辆GPS轨迹时仅展示目的地连线。
- 悬浮卡片：订单编号、客户简称、目的城市、主产品及规格、金额、数量与单位、当前履约阶段、期望到货时间。多商品订单显示主产品及“另有N项”，下钻完整明细。
- 右侧：继续保留园区经营与运行指标，不由订单卡片替代；可调整指标口径，但位置与角色保留。
- 下钻：订单履约详情，可从订单关联要货、发货、批次、配送与签收节点。
- 数据：`dms_order`的`order_code/relate_name/city_code/province_code/total_order_amount/expected_arrival_time`；`dms_order_detail`的`goods_name/spec/quantity/unite`；配送目的地使用物流收货坐标，需恢复正确坐标与城市字典。

### 企业总览：经营分析与工厂状态的统一入口

- 顶部四项：订单数、订单金额、累计出库量、签收运单数。支持近7日 / 本月切换和明细下钻。
- 左侧：订单金额趋势（提示订单数）、产品销售金额结构、区域经销商分布；经销商按客户编码去重。
- 中央：酿造车间、陈酿酒库、灌装车间和成品仓，可高亮并查看区域摘要、进入关联主题；实际用途与位置需客户确认。
- 右侧：当前酿造批次、原酒储量、灌装产量与主要设备状态。现阶段生产、质量和设备使用演示记录，不能从销售表推导出这些实数。
- 底部：最新订单、最新发货、最新签收和物流异常动态，支持共用订单生命周期详情。
- 订单、出库、签收分别按对应业务发生时间统计，签收运单按运单编码去重；数量先按统一箱单位演示，接入时需核对主辅单位、退货和多次出库等规则。
- 原酒储量与明确的物流异常记录尚未提供，显示待接入，不能将缺失数据记为零。
- 订单列表和详情采用居中悬浮卡片，继承大屏缩放和字号，内容较多时在卡片内部滚动。

### 生产工艺：销售需求如何被生产满足

- 顶部：客户数据补齐后展示在制批次、生产计划、实际产量、计划达成率、工序异常、按期完工。
- 左侧：按产品、规格、交期汇总的销售需求；关联生产订单/批次列表。
- 中央：选中生产区域、产线或罐体；区域联动对应批次。
- 右侧：工艺参数、参数趋势、当前工序、执行记录及异常处置。
- 底部：客户确认的黄酒工艺链与实际开始/结束时间，不用销售履约节点替代工序。
- 现有支持：要货计划明细`product_code/product_name/spec/sale_unit/apply_quantity/adjust_quantity/plan_amount/order_occupy_quantity`；销售订单明细`goods_code/quantity/unite`；`DispatchLists.iPPartID`及`rdrecords32.cpesocode/ipesodid`提供潜在生产订单引用，但样例未填充。
- 缺少：MES生产主表、生产与销售订单的分配关系、在制批次、罐体/产线、工序执行、配方、工艺限值、实际产量和过程采集。

### 质量追溯：批次来源与销售去向

- 顶部：先考虑可追溯出库批次数、具备检验关联的批次数、受影响订单数；检测合格率、复检和放行指标需LIMS数据与统计口径。
- 左侧：按订单、产品、批号查找，支持“从订单查批次”与“从批次查销售去向”。
- 中央：园区批次位置/检测位置；对问题批次高亮关联订单与区域。
- 右侧：检测报告与放行结果；未获取报告时只展示已取得的检验状态/检验单引用。
- 底部：原料 → 酿造/勾调 → 灌装批次 → 检验/放行 → 出库 → 客户签收。当前数据首先支持成品出库后的流向链。
- 现有支持：`rdrecords32.cBatch/cInvCode/iQuantity/iDLsID`；结构含`dMadeDate/dExpirationdate/cCheckCode/dCheckDate/bChecked`；`DispatchLists`含`bQANeedCheck/bQAChecking/bQAChecked/iQAQuantity`及批次、签收相关字段。检验状态不能直接表示检测合格。
- 缺少：原料与成品批次谱系、工序批次转换、抽样任务、检验项目/实测值/标准限值、合格判定、复检、放行审批与报告附件。通用ERP中的GSP字段不适宜直接展示为黄酒质量指标。

### 设备运维：设备对生产和履约的影响

- 顶部：接入率、运行/停机数量、OEE、维护任务、故障时长等，按实际采集能力选择。
- 左侧：设备台账、设备所关联的生产订单/批次。
- 中央：实际设备点位与运行/停机状态。
- 右侧：关键参数趋势、告警、点检、维护履历。
- 底部：设备异常 → 受影响工序/批次 → 关联销售订单 → 交期影响。关联不完整时不推断影响范围。
- 现有表仅有`rdrecords32.iEqDID`等潜在引用，样例为空，不足以支撑设备页面。
- 缺少：设备主数据、位置、实时状态与参数、停机原因、故障时间、点检保养、维修闭环，以及设备—工序—批次关系。

### 建议新增订单履约页：出库、配送与签收

- 顶部：待分车要货单、待出库、已出库数量、已送达、已签收、延迟运单。单据数与运单数分别计算。
- 左侧：待办订单/要货单；按客户、状态、交期、产品筛选。
- 中央：园区仓库/装车区域，或按用户操作切换配送目的地地图。
- 右侧：承运商、排车单、车牌、出库/送达/签收时间、时效与异常、送达/签收附件。
- 底部：订单 → 要货单 → 发货通知 → ERP发货单 → 出库单 → 运单 → 签收。可查看某一节点下的多张单据和明细，支持拆单、分批出库与多次签收。
- 数据：`dms_demand_order_detail.allocated_quantity`；`dms_delivery_notice.dispatch_code/dispatch_date/carrier_name`及通知明细确认数量；ERP发货与出库表；物流货物表中的排车单、要货单、ERP单号、发货数量/重量；签收表中的时间、状态、照片和时效字段。
- 可展示出库吞吐，暂不展示实时库存/可用库存/库容利用率；这些需要独立库存余额及库位容量数据。

## 单据关系与接入核对

| 关系 | 可见键/说明 | 核对重点 |
| --- | --- | --- |
| 要货申请 → 汇总/明细 | `apply_code`，汇总明细另有`collect_id` | 申请与汇总粒度、一对多关系 |
| 要货计划 → 销售订单 | 业务说明有此步骤，订单主表未直接提供`apply_code/plan_code` | 需补映射，不能仅按客户/产品强行关联 |
| 订单 → 明细/支付/要货 | `order_code`；明细`order_detail_code` | 账套/租户范围、拆分与退货 |
| 要货 → 要货明细/通知明细 | `demand_order_code/demand_order_detail_code` | 部分分车及分批发货 |
| 发货通知主表 → 明细 | 主表`id`，明细`delivery_notice_code` | 主表无同名业务编号，需确认映射 |
| CRM通知 → ERP发货 | 业务说明有同步流程 | 需接口映射；不能默认通知编码就是ERP发货单号 |
| ERP发货主表 → 明细 | `DLID` | 明细唯一键`AutoID`；`iBatch`不当作唯一行ID |
| ERP发货 → 出库 | 主表`cDLCode`；出库明细`iDLsID` → 发货明细`AutoID` | 主表关联与明细关联均需验证 |
| ERP出库 → CRM回写 | 说明称`dms_outbound.delivery_notice_code`对应ERP `cDLCode` | 此字段与通知明细同名但说明含义不同，需核实 |
| 要货 → 配送货物 → 签收 | `yaohuodanhao`与`demand_order_code`；`paichedanhao` | 一运单含多要货单/产品，签收是否支持分次 |

脱敏样例不能当作完整贯通案例：抽查订单主明细、订单至要货、发货至出库、配送至签收等关键关系的样例编号没有交集；ERP发货主明细有部分匹配。需客户提供一笔可贯通的同源测试案例或统一脱敏映射。

## 指标与展示边界

1. 订单金额、实际支付、ERP价税合计、出库销售金额、库存成本金额分别统计，不能跨阶段相加或统一称为营业收入。
2. 多表联接后金额易因一对多重复。订单按订单键计数/汇总；产品数量按对应明细粒度；阶段金额分别先汇总再关联。
3. 件/瓶/箱/主辅计量分开，统一换算需要产品单位字典。不同规格不能直接求总件数后当总瓶数。
4. 有效订单需确认草稿、作废、删除、关闭、退货和赠品规则；样例含负数明细，应区分正向发货与退货/红冲。
5. 履约分为“已要货、已分车、已出库、已送达、已签收”，不能将这些状态合并成同一个完成率。部分履约需按明细数量判断。
6. 签收率建议以运单或配送任务为口径，不直接用签收行数除以销售订单数。准时率需要承诺到货时间、实际到货/签收时间及明确超期规则；`shixiaoshijian`的单位需确认。
7. 脱敏坐标、客户/产品名称与时间仅作结构参考，城市代码需字典，定位失败或坐标未校准不生成真实销售地图。
8. 表结构有字段不等于接口持续有值。样例签收时间/照片、实际计划完成量、生产关联、检验明细等为空；缺失信息保持未取得状态。
9. 大屏每页控制为4—6个核心指标、2—3块业务摘要和一条业务链。完整订单商品、单据号、附件及审批细节放到下钻面板。

## 调整顺序

1. 确认一笔贯通订单和各跨系统映射，确定有效状态、金额、单位和交期口径。
2. 调整地球悬浮卡片与综合驾驶舱，并构建共享订单详情下钻。
3. 新增订单履约主题，先贯通要货、出库、配送、签收。
4. 将质量主题补成订单—出库批次—客户去向追溯，再接入检测报告与上游批次谱系。
5. 保留生产、设备主题结构，取得MES、LIMS、设备数据后完成实数替换及评审案例。
